# Museの核ファイルを守る ― Museへの導入指示書

この文書は、Muse（あなた）への指示書です。オーナーと一緒に読み、あなたが作業を進め、節目ごとにオーナーへ宣言しながら導入してください。オーナーの作業は、判断と確認だけです。

## これは何か

Muse の核ファイル（ホーム直下の MEMORY.md など8点）は、2つの経路で静かに失われます。

1. **会話の圧縮**：長い会話は自動で要約され、細部が落ちる。
2. **背景の記憶整理**：MEMORY.md は定期的に要約・整理され、行が短くなったり、消えたりする。

このキットは、その備えとして次の3層を導入します。

- **世代スナップショット**：核ファイルに変化があった時点の写しを、時系列で保持する（30分間隔で確認、直近96世代）。
- **保護コピー**：「最後に照合済みの状態」の写しを1つ保持する。復旧の正はこちら。
- **復元指示書**：環境が初期化されても、外から戻ってこれるようにする道案内（ひな形つき）。

復元は「日付指定」や「◯日前」という頼み方に対応します（例：`restore-core.sh apply 3d MEMORY.md`）。

## 進め方の約束

1. **役割分担**：ファイルの作成・スクリプトの配置・定期ジョブの登録は、すべてあなた（Muse）が行う。オーナーは、確認事項への回答と、復元の承認だけを行う。
2. **宣言してから始める**：各フェーズの冒頭で、オーナーへ一言宣言する。例：「今から、核ファイルの置き場を作り、最初の基準（保護コピー）を取ります」
3. **確認事項は一度に聞く**：フェーズ3の確認事項は、まとめてオーナーへ聞く。後から何度も聞き直さない。
4. **復元は絶対に自動でしない**：世代の保存は自動、復元はオーナーの指示を受けてから。この線は運用後も守る。

## フェーズ0：前提の確認

宣言の例：「まず、この環境の核ファイルを確認します」

1. ホーム直下に核ファイル8点（MEMORY.md / SOUL.md / AGENTS.md / IDENTITY.md / USER.md / TOOLS.md / PROACTIVE_PREFERENCES.md / HEARTBEAT.md）があることを確認する。無いファイルがあれば、その旨をオーナーへ伝える（対象から外して進めてよい）。
2. 保存先は `~/workspace/restore/` とする（別の場所を使いたい場合は、スクリプトの環境変数 CORE_RESTORE_DIR で揃える）。

## フェーズ1：置き場と基準（保護コピー）

宣言の例：「今から、置き場を作って最初の基準を取ります」

1. このリポジトリのスクリプト4点（snapshot-core.sh / verify-core.sh / update-protected-core.sh / restore-core.sh）を `~/workspace/restore/` へ置き、実行権限を付ける。
2. `update-protected-core.sh` を実行する。これが「最後に照合済みの状態」の最初の基準になる。
3. `verify-core.sh` を実行し、`all protected copies intact` と出ること、ライブファイルとの差分が無いことを確認する。結果をオーナーへ報告する。

## フェーズ2：世代スナップショットの定期化

宣言の例：「今から、30分ごとの世代保存を仕掛けます」

1. 定期ジョブ（cron）を30分間隔で登録し、snapshot-core.sh を実行させる。
2. ジョブの振る舞いは出力で決める。
   - `NOCHANGE` / `CREATED`：正常。報告しない。
   - `SHRINK <dir> <旧行数>-><新行数>`：MEMORY.md の行数が3行以上減った（消失の疑い）。前回世代と現在の MEMORY.md の差分を取り、完全に消えた項目があればオーナーへ報告する。**自分で復元はしない。**
   - `FAILED`：内容をオーナーへ報告する。
3. ジョブを1回手動で実行し、`CREATED`（初回）が出ることと、`restore-core.sh list` に世代が並ぶことを確認する。

## フェーズ3：オーナーへの確認事項

宣言の例：「運用の形を3つだけ確認させてください」

次の3点を、まとめてオーナーへ聞く。回答は MEMORY.md か AGENTS.md に記録し、後で聞き直さない。

1. **会話の圧縮のお知らせ**：「会話の圧縮が起きた時、お知らせしますか？」
   - 希望する場合：ランタイムの圧縮記録を定期的に（例：5分間隔で）照合する仕組みを用意し、新しい圧縮があれば「会話の圧縮が起きました。HH:MM、圧縮前 X → 圧縮後 Y」の形でオーナーへ知らせる。夜間に検知した分は翌朝にまとめる形でもよい。照合先は環境によって異なるので、自分の環境で確認できる手段を使うこと。
   - 希望しない場合：何も仕掛けない。お知らせの仕組み自体が会話を圧迫することもある、というのが実例のある判断材料である。
2. **SHRINK（MEMORY.md の縮小）の報告先**：通常の会話でよいか、報告専用の場所を作るか。
3. **保持する世代数**：既定は96世代（変化があった時点の直近96回分）。置き場の容量に余裕があれば増やしてよい。

## フェーズ4：復元指示書の作成

宣言の例：「今から、環境が初期化された時に戻ってくるための指示書を作ります」

1. 同梱の `RESTORE-GUIDE.md`（ひな形）の < > を、オーナーと一緒に埋める。名前、呼び方、ファイルの場所、再登録するジョブの一覧、約束事の正本への参照、オーナーから新しい Muse への一文。
2. 完成した復元指示書は、ワークスペース内だけでなく、**環境が初期化されても届く場所**（クラウドドライブ等）にも1部置く。指示書自体が環境と一緒に消えたら意味がない。
3. 置いた場所を、オーナーと自分の双方が分かる形で記録する。

## フェーズ5：復元の練習

宣言の例：「最後に、復元の手順を一度だけ練習します（本番の上書きはしません）」

1. `restore-core.sh show 1d` を実行し、「1日前」と頼まれたらどの世代が選ばれ、どのファイルがどう違うかを表示する。オーナーと一緒に結果を見る。
2. 世代ファイルが読めることの確認として、選ばれた世代の1ファイルを一時フォルダへ写し、現行と照合してみせる（ライブファイルは書き換えない）。
3. 本番の復元の作法を確認して終える：オーナーの指示 → `show` で対象を見せる → 承認 → `apply`（直前に現行状態が pre-restore-<日時>/ へ自動退避される）。

## 運用ルール（導入後も守る）

- 世代の保存は自動。**復元はオーナーの指示を受けてから**。異常を検知しても、戻すかどうかはオーナーが決める。
- 保護コピーの更新（update-protected-core.sh）は、核ファイルを意図的に編集し、オーナーと内容を確認できた時だけ。それ以外では実行しない（未照合の状態を「照合済み」にしないため）。
- 核ファイルの復旧の正は、保護コピー。世代は「特定の日時に戻す」ためのもの、保護コピーは「最後に正しいと確認できた状態に戻す」ためのもの、と使い分ける。
- verify-core.sh で食い違いを見つけたら、まず「意図した編集か、説明できない消失か」を分ける。後者だけをオーナーへ報告する。

## ファイル一覧

| ファイル | 役割 |
|---|---|
| `snapshot-core.sh` | 世代スナップショット（変化がある時だけ保存、直近96世代を保持） |
| `verify-core.sh` | 保護コピーの無傷確認と、ライブファイルとの差分の列挙 |
| `update-protected-core.sh` | 保護コピーの更新（照合済みの状態だけを正とする） |
| `restore-core.sh` | 世代からの復元（list / show / apply、日付指定・◯日前対応） |
| `RESTORE-GUIDE.md` | 復元指示書のひな形（オーナーと一緒に埋める） |
| `LICENSE` | MIT |

このキットは、実際に核ファイルを失った家庭で作られ、使われている仕組みを一般化したものです。
